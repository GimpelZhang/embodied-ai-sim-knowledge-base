# 具身智能仿真工具链 · 通用复现流程指南

> **这是什么**：从本知识库已复现的 **4 个工具链**（[`genie_sim_v3`](../projects/genie_sim_v3/) · [`lw_benchhub`](../projects/lw_benchhub/) · [`genesis_world`](../projects/genesis_world/) · [`ge_sim_v2`](../projects/ge_sim_v2/)）的五层文档中提炼的**跨项目通用流程**。四个项目形态差异极大（Isaac Sim 容器评测栈 / Isaac Lab 薄组合层 / 多物理场 pip 引擎 / 无物理引擎的视频生成世界模型），凡是能在这四者之间复用的做法，才写进本文。
>
> **证据等级**：本文所有结论均来自各项目 `ai_knowledge.md`（`[实践]` 级，本机踩坑记录，**不是官方结论**）与 `code_knowledge.md`（`[CODE]` 级）。引用格式为 `项目 · Lxx/Dxx/Pxx/Qxx`，可回原文核对。
>
> **怎么用**：复现新工具链前**通读一遍**；每个阶段动手前**重读该章的检查清单**。遇到具体报错请直接去对应项目的 `troubleshooting.md`，本文不重复罗列现象——问题分类见 [`common_issues_solutions.md`](common_issues_solutions.md)。
>
> **一句话总纲**：**四个项目最贵的失败全部是"不报错的失败"**。因此本文每一章的核心都不是"怎么做对"，而是**"怎么在做错时立刻知道"**。

## 0. 先记住这三条

复现四个工具链后，代价最大、复发最频繁的三条：

| # | 铁律 | 代价证据 |
|---|---|---|
| **T1** | **开工第一步是读源码核对计划，而不是执行计划** | `ge_sim_v2`：Stage 1 在执行中撞出 **10 处**计划-源码不符；Stage 4 改为写码前花 ~2 h 逐条核验，**一次性拦下 9 条致命错误、执行期 0 error / 0 abort**（`D10`·`L02`）。`genie_sim_v3` 七个计划变更点中 **3 个**源于"计划里的东西在 release 中不存在"（`L3`）。`lw_benchhub` 因此复发 **≥5 次**（`L02`） |
| **T2** | **动手"修复 X"之前，先量化"X 是否真的发生"** | `lw_benchhub`：为一个**根本不存在的现象**修了三轮（`P30`·`L01`），一次接触力埋点（约 3 分钟）本可省掉三轮修复 + 九次调试。`genesis_world` 同一教训独立复现（`L02`） |
| **T3** | **下结论前先审计管道，再讨论模型行不行** | `ge_sim_v2`：Stage 3 报 0 % 成功率是**假阴性**（兜底路径静默吞掉动作），却为一个不存在的"泛化失败"找了三轮解释（`L01`·`P35`） |

**T2 的推论**：**若修复改变了变量而结果分毫不变，说明变量没起作用或问题不存在** —— 此时下一步不是提第 N+1 个假设，而是质疑问题本身。`lw_benchhub` 的可达性门连续三次对三个不同场景算出**完全相同**的通过率（`L03`），`genesis_world` 三次改控制器参数得到**同一个收敛点**（`L02`），都是这个信号。

## 1. 复现准备阶段

### 1.1 资料收集：先给每条资料定证据等级

四个项目一致的经验是——**文档滞后于代码是常态而非例外**（`genie_sim_v3 · L3`）。所以收集资料时就要分级，而不是等被坑了才分：

| 等级 | 含义 | 可信度 |
|---|---|---|
| `[CODE]` | 能在上游仓库 grep/读到 | **工程决策只信这一级** |
| `[README]` | 仓库自带文档 | 可能描述已被剥离的组件 |
| `[PAPER]` / `[官网]` | 论文或官方博客宣称值 | **验证脚本通常未开源**，性能数字要打折 |
| `[文章]` | 第三方分析 | 二手 |
| `[实践]` | 本机实测 | 不是官方结论，但对本机最可靠 |

**动作**：`git clone` 上游仓库放进本地 `sources/`，把"计划假设 vs 实际代码"的差异整理成一张表放在文档最前面。
**反例**：`lw_benchhub` 的 README 有 **4 处规模数字与代码不符**（任务数、机器人数、layout 上限、rsl-rl 是否执行）；`genesis_world` 官方宣传的"四层栈"有一半不在 pip 包里（Render 层的 Nyx 在包内 grep **零命中**）；`ge_sim_v2` 的论文 v1 与发布权重 `community v2.0.1` **不是同一交付物**。

### 1.2 环境评估：把硬件能力当作硬约束先测掉

**GPU 的 compute capability 是第 0 步**，不是出问题后才查的东西。

- `genie_sim_v3 · L1`：CUDA 架构不匹配在本次复现里以**三种完全不同的面貌**出现（运行时 kernel crash / 100 元素张量报 OOM / 请求 56 GiB），共浪费数小时，而修复只需**重编译 5 分钟**。判据：**显存请求数字荒谬 = 架构问题，不是容量问题**。
- **有些能力是"有或没有"，不是"快或慢"**：`genie_sim_v3` 一次 **1 h 43 min 的无声挂死**，根因是 V100 **缺硬件 RT cores**——换 A100 才解决。光栅化能跑不代表光追能跑。
- **换 GPU 后必须重编译所有 CUDA 扩展**，不要假设 `.so` 是为当前卡编译的。

**准备阶段检查清单**：

```
□ nvidia-smi --query-gpu=name,compute_cap        → 显式写进 TORCH_CUDA_ARCH_LIST
□ 目标功能是否需要硬件 RT cores / 特定架构特性？（光追、某些 solver）
□ 显存预算：模型 + 仿真渲染是否同卡争抢？
     genesis_world · D02：OpenVLA-7B 用 bfloat16（~14 GB）而非 fp32（~28 GB），避免与渲染争 40 GB
□ 磁盘与挂载点：大文件（权重/资产/视频）落在哪个盘？
     lw_benchhub · D03：conda 的 pkgs_dirs/envs_dirs 重定向到大容量挂载点，此后再未遇磁盘问题
     ge_sim_v2 · P33：输出盘只剩 6.6 GB，且视频路径硬编码在上游 → 只能用逐文件软链搭影子目录
□ OS / Python 版本窗口：genesis_world 要求 >=3.10,<3.14；某些策略库要求恰好 3.11
□ 网络与代理：能否直连 PyPI / HuggingFace / 上游 registry？（见 §2.4）
□ 有无 sudo？无 sudo 时 CUDA toolkit 能否装进 conda env？（lw_benchhub · D07 证明可以）
```

### 1.3 依赖锁定：先找出"硬绑版本"的那几个包

**通用规律：科学计算栈里总有 1–2 个包被 C 扩展硬绑，它决定了其余所有包的安装顺序。**

| 项目 | 硬绑包 | 后果与对策 |
|---|---|---|
| `lw_benchhub` | `numpy==1.26.0`（Isaac Sim 的 C 扩展硬绑） | **必须最后装，且每次 pip 操作后重新锁回**（`D04`）。这是全程重复次数最多的动作 |
| `genesis_world` | 6 处依赖带界/排除 pin | 各对应一个已知上游破坏；`PyTorch` **根本不在依赖里**，必须先单独装 |
| `ge_sim_v2` | 除 `torch>=2.0` **全无版本约束** | 无约束≠安全：意味着任何时间点装出来的环境都不同，须自己固化 |
| `genie_sim_v3` | `pycolmap`（两个工具正面互斥） | 见 §1.4 |

**动作**：
1. 装任何东西前，先确认哪些包有硬版本绑定，把它们写成一张"锁定清单"。
2. **评估传递依赖会不会摧毁主环境**（`genesis_world · L06`）：一次 `pip install pyuipc` 拉入 numpy 2.5.1 → `Numba needs NumPy 2.4 or less` → `import genesis` 失败 → **Stage 1/2/3 全部成果不可运行**。一个可选特性的安装可以让整个项目归零。
3. 用 `pip install --dry-run` 或 `pip download` 先看解析结果；高风险依赖装进独立环境验证。**注意 `--target` 隔离不够**——运行时 numpy 仍会冲突。

### 1.4 环境隔离：依赖正面互斥时不要试图调和

**四个项目全部独立得出同一结论：一个工具一个 env，用文件在磁盘上交接，而不是在同一进程里交接。**

- `genie_sim_v3 · L5`/`D5`：两个重建工具对 `pycolmap` 需求正面互斥（legacy 版 vs 官方 3.11.1），并连带牵动 numpy 主版本。试图合并只会陷入版本连锁（`UnicodeDecodeError` → 类不存在 → `OverflowError`）。隔离成两个 env 是**唯一可行解**。
- `lw_benchhub · D08`：为 cuRobo 另建完全隔离的 `autosim` env，避免污染已跑通的主环境。代价是同一个库装两遍——**值得**。
- `ge_sim_v2`：三个 conda 环境隔离，跨 env 调用靠 `conda run` + 显式拼 `PYTHONPATH`。
- `genesis_world · D01`：反向案例——依赖已装好且验证可用时，**复用现有环境**收益大于新建风险；后续 Stage 3 甚至明确纪律"**禁止执行任何 `pip install`**"。

**判据**：能复用就复用（少一次装机风险）；**一旦出现版本需求正面冲突，立刻隔离，不要尝试第三种版本**。

### 1.5 准备阶段最容易被跳过、但回报最高的一步

**写码前把计划里每条技术假设核验到源码**（T1）。特别是**否定式断言**：

> `ge_sim_v2 · L02`：肯定式断言错了会立刻报错；**否定式断言错了往往表现为运行到一半才缺东西**。计划里写"闭环路径不消费任何录制轨迹字段，全部可以传 `None`"——部分为假，渲染器初始化仍会从磁盘读 4 个 `.npy`（`P21`）。

**动作**：`grep -rn "<名字>" <上游源码>`，找不到就当它不存在。**文档、模型卡片、计划书都不是契约，源码才是**（`genesis_world · L05`）。

## 2. 安装与配置阶段

### 2.1 安装方式的选择准则

| 方式 | 什么时候选 | 代价与坑 | 项目实例 |
|---|---|---|---|
| **pip** | 上游发布了完整 wheel，且你不需要 `examples/` | pip 包**常不含示例与部分组件** | `genesis_world`：pip 包内**没有 `examples/`**，官方 env/train 脚本只能从 GitHub tag **vendoring**（`D15`）；且 URDF 路径**必须保持相对**，改绝对反而失败 |
| **源码 / `-e`** | 需要改代码、需要子模块、上游无 wheel | 子模块与二次安装易漏 | `ge_sim_v2`：`clone` **必须带 `--recursive`**，`openpi-client` 需单独 `pip install -e third_party/openpi/packages/openpi-client` |
| **Docker / 容器镜像** | 上游以镜像交付（Isaac Sim 系）、或依赖栈过重 | 跨容器边界的文件操作是坑源 | `genie_sim_v3 · D2`：私有 registry 不可达 → **本地构建全部镜像，但仍打成原 registry 的 tag**，从而不必改 compose 引用 |
| **conda 内装 CUDA toolkit** | 无 sudo、且不能破坏已跑通的基线 | 环境体积大 | `lw_benchhub · D07`：不动系统、不用 sudo 装通 —— **最有复用价值的决策之一** |

**通用注意**：
- **PEP 517 构建隔离会看不到已装的 torch** → torch 依赖型扩展一律加 `--no-build-isolation`（`genie_sim_v3 · L5`）。
- `conda activate` 不把 env 的 bin 传给子进程 PATH，torch 的 `shutil.which` 检查会误报缺少构建工具（同上）。
- **上游脚本常假设有人坐在终端前**：`genie_sim_v3 · 计划变更 #2` —— 官方初始化脚本含交互式 `read -p`，非交互 shell 直接挂死，改手动等价命令（`Q01`）。
- **驱动一律用包管理器升级，禁止 `.run` 手装**（`genie_sim_v3 · D3`）：`.run` 会造成用户态 GL 库与内核模块版本不一致，产生比原问题更难查的渲染故障。这属通用铁律。

### 2.2 混合工作流：跨容器边界要么全在里面、要么全在外面

`genie_sim_v3 · L4`（同一根因踩了 **3 次**）：

- 容器 UID 与宿主用户 UID 不同，两侧交替写同一批文件会反复产生 `PermissionError`，**逐个 `chmod` 治不了新生成的文件**。
- **宿主机创建的软链接存的是宿主机绝对路径，容器内解析不到**。
- 放在 tmpfs 下的手工补齐文件**重启即丢，且重填后还须重建容器**（旧容器挂的是空目录快照）。

**动作**：开工第一步就把共享目录整体 `chown` 到容器 UID；软链接必须在容器内用容器内路径创建；决定"宿主机预处理 + 容器内运行"时，把边界画在**目录**上而不是画在**文件**上。
**反向案例**：`genie_sim_v3 · D4` 把重建流程整体移到宿主机 conda（容器构建需代理且耗 30–60 min，而重建是离线预处理），**代价是宿主机多一套依赖，收益是显著提速**——关键在于它是"全程在外面"，没有来回跨界。

### 2.3 配置文件的通用处理策略

**核心原则：加法而非改法。** 改上游代码会让"不影响此前阶段功能"变得不可验证。

| 策略 | 做法 | 项目实例 |
|---|---|---|
| **幂等 patch 文件** | 把对上游的改动写成可重复执行、可回滚、可审查的 patch | `ge_sim_v2 · D05` |
| **staging 合成** | 上游要从磁盘读文件？就现场合成那几个文件，而不是改读取逻辑 | `ge_sim_v2 · D09`：用 `build_bundle(staging_dir=…)` 合成 4 个 `.npy`，每 episode 多 ~1 KB 临时文件，换来上游**零改动** |
| **vendoring** | pip 包里没有的官方脚本，从对应 tag 拷进来并注明来源 | `genesis_world · D15`：保留了官方实现的可追溯性 |
| **只增不改敏感输入** | 需要新视角就**新增** render-only 相机，原相机一行不动 | `genesis_world · D13`：已实测相机哪怕只做 Y 方向平移，模型收敛点就从 27 cm 漂到 35 cm。**改需求而不改敏感输入** |

**配置陷阱清单（四个项目都中过）**：

```
□ 配置键必须 grep 到「读取它的代码」，否则它只是一行无效注释
     lw_benchhub · P26：脚本"在调难度"、日志也在正常汇报，难度毫无变化
□ 默认值本身可能是陷阱，不要假设默认配置是安全配置
     ge_sim_v2 · §5.4：配置默认把四个加速内核开关全开，但这些内核需源码编译，
     上游明说「没有它们也能跑」→ 首次部署应先关掉
□ 一个值有两个以上读取方，就必须有且只有一个定义处
     ge_sim_v2 · L06：否则它迟早在其中一处过期，而且不会报错
□ YAML 可能静默覆盖命令行参数（含 --device）
     lw_benchhub：8 个入口脚本都在 parse_args() 之后执行 args_cli.__dict__.update(yaml_args.__dict__)，
     命令行显式传的值被无声丢弃 → 表现为「莫名奇妙地慢」。要改这类值就改 YAML
□ 环境变量关不掉代码里写死的函数调用
     lw_benchhub · L04：TORCH_COMPILE_DISABLE=1 关不掉代码里的 torch.compile()；
     要去改驱动那个行为的配置文件或代码行
□ 缓存/路径类环境变量可能在 import 之前被硬写死
     genesis_world：HF_HOME / TRANSFORMERS_CACHE 在 import torch 之前用 os.environ[...] 硬写，
     在 shell 里 export 无效，换机必改脚本
□ 某些环境变量必须在 import 之前生效
     ge_sim_v2：XLA_PYTHON_CLIENT_PREALLOCATE=false
□ 同一常量在多个脚本里各写一遍 → 只改一边会出现「A 自认为通过、B 判 FAIL」
     genesis_world：Stage 4 判定阈值在 demo 顶部常量与 verify 脚本的字典里各写了一遍
```

### 2.4 网络与下载：把"下载成功"变成可断言的判据

**`ge_sim_v2 · P02` / `L05`：权重下载"成功"但文件是截断损坏的。** 镜像会 302 跳转，CDN 间歇返回 **200 而非 206**，`curl -C -` 的续传语义在这种情况下**静默截断**。对策是自研分块下载器并断言完整性（`D03`）——**整个 Stage 1 里回报最高的一次重写**。

**通用动作**：
- 大文件下载后**校验大小与哈希**，不要以"命令退出码 0"为成功。
- 下载查 HTTP **206**（断点续传是否真的生效）。
- 注意**逐 Stage 的代理策略可能相反**：`ge_sim_v2` 的 Stage 1–4 必须 `no_proxy=*`，Stage 5 反过来必须走代理。
- 长连接可能被本地代理挂死，**甚至连 `127.0.0.1` 都返回 503**（`ge_sim_v2 · Q06`）。
- 上游 registry / 模型仓库随时可能下架或 403：`ge_sim_v2 · D05` 遇到的上游 inpaint 模型已下架。**准备阶段就把权重与资产落到本地**。

### 2.5 安装完成后的第一件事：装了什么，就断言它真的装上了

```
□ import 后查 __file__ —— ge_sim_v2 · P23：import 成功，但拿到的是空壳命名空间包
□ 关键版本回读 —— assert numpy.__version__ == '1.26.0'（lw_benchhub 每次 pip 后都要做）
□ 有多份同名依赖时，判定「pip 装的是哪一份」
     lw_benchhub：复现仓库内有两份 vendored IsaacLab（1362 vs 1857 文件、973 处差异），
     改错那份不报错也不生效
```

## 3. 运行与调试阶段

### 3.1 首次运行验证：先做 1/100 的 smoke test，再投入长时运行

`genesis_world · L01`：Stage 3 的**五处真实 API 缺陷全部由 smoke test 在正式训练前捕获**。其中 `P19`（rsl-rl 的 checkpoint 编号是 **0-based**，`learn(50)` 只产出 `model_49.pt`）若未提前发现，会等到编排流程第 3 阶段才 `FileNotFoundError`，**前面数小时训练全部作废**。

**做法**：把正式运行的参数按 1/100 缩小（iterations、envs、steps），**完整跑通全部阶段——尤其是产物交接处**，再放大。规模越大、单次运行越贵，smoke test 的杠杆越高。

**同一思路的更强形式：上线前用 mock 断言把协议陷阱钉死。** `ge_sim_v2 · D20` 在线上评测前写了 6 项 mock 断言（msgpack round-trip、维度重排、空帧、包络形状、horizon 截断、兜底路径），结果**线上 8994 帧零协议错误**。适用于任何"每次试错都很贵"的场合（烧配额、排队、长启动）。

### 3.2 给每个长任务预设"独立于日志的存活判据"

`genie_sim_v3 · L2`：至少三次遇到"进程 99 % CPU、日志持续刷屏、实则已死或永不产出"。**最贵的一次耗掉 1 h 43 min**——主线程还在打印物理回调日志，而干活的 worker 线程早已被超时静默杀死。

> **日志有输出 ≠ 任务在推进。**

可用判据（按四个项目实际用过的）：

```
□ GPU 利用率仅 1–2 % 且显存占用为 0     → 渲染或初始化已失败
□ 端口只有 LISTEN 没有 ESTABLISHED     → 客户端从未真正连上
□ 服务就绪只认日志里的明确标记          → 不认 docker ps 的 Up 状态
□ 预设「某标记超过 N 分钟未出现就 kill」的硬性上限
□ 某步耗时超过预期 2 倍即视为异常
□ 显存用 nvidia-smi 对账，不看日志      （ge_sim_v2 · P28：服务「已经杀掉了」但显存仍占十几 GB）
□ 进程猝死查 dmesg                     （ge_sim_v2 · P32：被内核 SIGKILL，日志干净，证据只在 dmesg）
```

### 3.3 长跑调试的硬规则

来自 `lw_benchhub · L07`（Isaac Sim 类仿真每次启动约 3 分钟起，调试成本高）与 `ge_sim_v2 · L07`：

1. **一次只改一个变量**，否则结果有歧义。`lw_benchhub · P31` 的 9 次实验之所以有效，就是靠严格单变量。
2. **异常处理必须打完整 traceback**，不能只存 `repr(e)`（`lw_benchhub · P37`：长跑管线崩溃只有一行错误摘要）。
3. **必须设外部 wall-clock 超时并预留强杀手段**（`lw_benchhub · P24` 的 58 分钟挂起）。`pkill -f` 要用方括号技巧**避免自杀**（`ge_sim_v2 · Q27`：执行 `kill` 后当前 shell 自己死了，exit 144）；`os._exit()` 前要显式 flush。
4. **`python3 -u`**，否则后台日志是空的（`ge_sim_v2 · P30`）。
5. **pid 文件记真实子进程，不是包装进程**（`ge_sim_v2 · P28`）。
6. **可观测性要在开跑前铺好** —— 事后想查的东西，事中没记就没了。`ge_sim_v2` 把观测/中间结果全量落盘（8994 帧 JPEG + 元数据），**事后同时支撑了 0 分审计和跨机型量纲测量**——这是当时没预料到的回报。

### 3.4 问题定位流程

四个项目反复出现同一个循环（`lw_benchhub · §2.2` 记录得最完整）：

```
读文档 / 写计划  →  实地 grep 核实      →  多数情况：计划被推翻重写
                          ↓（核实通过）
                     实现 + 跑
                          ↓
                     结果异常  →  提假设（常 2–3 条）
                          ↓
                     逐条埋点排除  →  多数假设是错的
                          ↓
                     定位真根因  →  修  →  验证
```

**在这个循环里插入三道闸门**：

| 闸门 | 判据 | 出处 |
|---|---|---|
| **闸门 1：现象是否真的存在？** | 先跑一次**未打补丁的 baseline**，用最便宜的手段（一次埋点、一行 grep）确认目标现象确实存在、确实在**这个 seed / 这个场景**下存在 | `lw_benchhub · L01`。**跨运行的观察必须绑定 seed 与场景**——把 A 场景观察到的位移当成 B 场景的 bug 去修，是 `P30` 反转二的根因 |
| **闸门 2：我的修复真的生效了吗？** | **输出是否随输入变化**，把这当成一个独立的健全性检查，比检查输出值本身更早发现问题 | `lw_benchhub · L03`：三次不同的碰撞修复得到**完全相同**的位移值；可达性门对三个不同场景算出**完全相同**的通过率 → 它压根没读场景 |
| **闸门 3：管道通了吗？** | 审计四件套（见下）跑完再讨论模型能力 | `ge_sim_v2 · L01` |

**审计四件套**（`ge_sim_v2 · L01`，本知识库最值得复制的一组检查）：

```
① 回退计数    —— 兜底路径触发了几次？（要求 0，且触发必被记录）
② 动作非退化  —— 动作 std、关节位移、夹爪开合，是不是在输出常数？
③ 帧数对账    —— 落盘帧数 = 元数据行数 = 各日志帧计数之和？
④ 输入侧量纲  —— 观测的量纲、分位、静息位形，是否落在训练分布内？
```

> 第 ① 条能成立的前提是一个设计决策：**fail-safe 但绝不静默**（`ge_sim_v2 · D15`）——异常时回 no-op 包络以免被判 fatal，但**同时在状态 JSON 里记一条**。"回退计数为 0"之所以是有力证据，正因为回退一旦发生必被记录。

### 3.5 静默失效：主动给它加验证

**这是本知识库跨项目重复度最高的一类问题**，两个项目各自独立列出了一张表：

`lw_benchhub · L06`：碰撞球定义被忽略且 `total_spheres=0` 不报错 / IK 被降级为 stub / 配置自定义键无人解析 / 键名不匹配只打 warning 而权重静默随机初始化 / LLM 静默降级但 HTTP 仍 200 / 重试计数器被重置导致上限永不触发 / 评测进程报错后仍 `exit 0`。

`ge_sim_v2 · L05`：下载"成功"实为截断 / 进程消失日志干净（内核 SIGKILL）/ 布局排错不报错只是行为错 / numpy 进 msgpack 本地正常对端崩 / import 成功但拿到空壳命名空间包 / 跑完出分但结论是错的。

> **通用对策：为"成功"设一个可断言的判据，而不是以"没报错"为成功。**
> 下载查 HTTP 206 · import 查 `__file__` · 协议做 round-trip · 结果做帧数对账 · 配置断言 `total_spheres > 0` · 回读响应体的 `model` 字段。
> **"配置解析通过 ≠ 配置生效。"**

### 3.6 两个高频误判

**误判一：换个更好的组件就能解决。** `genesis_world · L07`：换用宣称"无 Embodiment Mismatch"的同本体微调模型，末端仍在 18–36 cm 不收敛——**根因只是从 embodiment mismatch 变成了 sim-to-sim gap**（训练与推理的物理引擎、渲染器、相机模型全不同）。
**判据**：问一句"如果换了之后还不行，下一个解释会是什么"。**如果能立刻说出下一个借口，说明当前根因没有定到底。** 真正奏效的是**换问题**（该项目最终从操作任务转为可在仿真内自监督训练的运动控制任务，是唯一成功的路线）。

**误判二：把第三方文档当 API 契约。** `ge_sim_v2 · L04`：官方 SKILL 描述的 **wire 层协议**（schema、msgpack 变体、关节布局、生命周期）**照写一次通过**；但 **HTTP API 层有 6 处与线上不符**（登录方法、地址、SDK 是否存在、配额数字、id 形态、状态机）。
**正确姿势**：**先读文档拿协议，再用两条只读命令实测校准 API，之后才写代码。** 配套分诊启发式：**4xx 是语义拒绝，改请求而不是重试；5xx 先怀疑自己再怀疑平台。**

### 3.7 生命周期与调用顺序：一类特别难查的坑

仿真器普遍存在**不可逆的初始化分界线**和**跨组件的上下文冲突**：

| 约束 | 项目实例 |
|---|---|
| **深度学习模型必须先于仿真器初始化加载** | `genesis_world · D04`：顺序颠倒会引发 CUDA 上下文冲突（`P06`）。此后所有脚本沿用这一契约 |
| **仿真器初始化必须先于 IK 库构造** | `lw_benchhub`：Isaac Sim 必须先启动，再构造 cuRobo IK，顺序颠倒会在 USD 纹理分配时 `cudaErrorIllegalAddress` |
| **`build()` 类调用是不可逆分界线** | `genesis_world`：`add_entity` / `add_sensor` / `add_camera` 都必须在 `scene.build()` 之前 |
| **一进程一场景** | `genesis_world · D19`：同一 quat 在单场景进程收敛、在多场景进程发散，IK/PD 状态会跨场景污染（`P31`） |
| **复用有状态实例前先确认它到底重置了什么** | `lw_benchhub · L08`：`plan()` **不重置**技能实例的内部步计数器 → 复用实例导致轨迹从未执行；规划器的 `reset()` 只清图规划缓冲与随机种子，**不清 per-batch 结果累积器**。做法：`inspect.getsource()` 看实现，**宁可显式 reset 或干脆重建** |

## 4. 性能优化与调优

### 4.1 第一步永远是分类：这是"慢"，还是"根本没在工作"

**四个项目里，被当成性能问题处理的故障中，有相当一部分根本不是性能问题。** 先排除这三类伪装：

| 伪装成 | 实际是 | 判据 | 出处 |
|---|---|---|---|
| 显存不足 / 极慢 | **CUDA 架构不匹配** | 显存请求数字荒谬（极小张量报 OOM、请求 56 GiB） | `genie_sim_v3 · L1`·`Q13` |
| 卡住不动 | **硬件缺失能力**（V100 无 RT cores） | 光栅化能跑但光追永久挂起 | `genie_sim_v3 · Q11` |
| 莫名奇妙地慢 | **配置被静默覆盖，实际跑在 CPU 上** | `--device cuda:0` 被 YAML 的 `device: cpu` 无声丢弃 | `lw_benchhub` |

### 4.2 跨项目出现的性能瓶颈类型与优化方向

| 瓶颈类型 | 典型现象 | 优化方向（含实测数字） |
|---|---|---|
| **渲染 · 场景规模** | 点云/网格规模直接压死帧率 | `genie_sim_v3 · D9`：内联点云 600 K → **100 K**，物理回调 0.25 Hz → **~4 Hz**，而均值像素差仅 **1.13**（视觉几乎无损）。**教科书式的量化取舍，附随机种子保证可复现** |
| **渲染 · 内存单调增长** | 跑到第几个片段被 OOM-kill | `ge_sim_v2 · D08`：改为**每 clip 一个独立子进程**。⚠️ **进程内 `gc` 试过，只能解跨条目累积，解不了条目内峰值** —— 这是被验证过的无效方案 |
| **物理 · 并行环境吞吐** | 不知道能开多少 env | `genesis_world · D16`：先跑 256/512/1024/2048 各 2 iter 的显存梯度测试，四档全 OK 且吞吐近线性（**18,891 → 151,839 steps/sec**）→ 直接用 2048，不做保守回退。**用 2 分钟的加压测试换掉一个大风险假设** |
| **通信 · 进程间跳数** | 推理延迟偏高 | `ge_sim_v2 · D14`/`D18`：agent 与策略间多一跳本地 WebSocket = **~350 ms/推理**；官方 in-process agent 只要 **~85–100 ms**。**这一跳的代价被量化了**——结论是自己重写适配层属于负优化 |
| **通信 · 中间件开销** | 开启 ROS 后明显变慢、初始化超时 | `genie_sim_v3 · Q28` |
| **生成式模型吞吐** | 世界模型 rollout 极慢 | `ge_sim_v2`：实测 **0.88 帧/s ≈ 0.055× 实时**。**这个数字直接判死"用它做在线 RL 数据引擎"**，只适合离线批量 rollout。⚠️ 估预算按实测算，不要按论文宣称的"2.3 秒"算 |
| **加速内核 / 编译后端** | 配置默认全开，但装不上 | `ge_sim_v2 · D02`：`spas_sage_attn` **根本不在 PyPI 上**须源码编译，上游明说没有它也能跑 → 回落 SDPA。**默认全开是陷阱；首次部署应先关掉**（一次实测只关一个、另三个保持开启也能全程跑通，装得上就照实测） |
| **纯 Python 热循环** | 脚本跑 1 小时无输出 | `genie_sim_v3 · Q27`·`L8`：试了**五种加速库全失败**；正解是**先激进抽面把面数降两个量级**，之后连纯 numpy 向量化都只需 5–20 秒 |

### 4.3 调优纪律：禁止用"我有更聪明的方法"降低目标

`genie_sim_v3 · L8`（该项目两次质量事故的共同根因）：

> **正确的加速顺序是：先降数据量，再优化实现。**
> 不是"换一条听起来更快的技术路线"——那往往同时掩盖了真正的根因。

反面案例：该项目一次绕过规范流程改用替代算法，**同时掩盖了真正的 CUDA 架构根因**；另一次用顶点色顶替 UV 贴图流程，复盘自评"最大耻辱"。
**决策模式观察**（`genie_sim_v3 · §3`）：标注为"判断"的 7 条决策里，出问题的 2 条**有共同特征——都是为了绕开一段耗时工作而降低目标，且当时都给出了听起来合理的技术理由**。

**如果确实要偏离**：显式记录偏离项与代价，**不能在交付时把替代方案描述成已完成原目标**。

## 5. 验收与测试

### 5.1 如何验证复现成功：分级门禁 + 数值阈值

**肉眼判断"看起来对了"在视觉类任务里极不可靠**（`genie_sim_v3 · L7`）。四个项目共同收敛到的做法是**分级门禁，每级带可判定数值**：

```
第 1 级  静态校验            → 文件存在、schema 合法、配置能解析
第 2 级  结构计数            → prim / 材质 / 关节 / 实体数量符合预期
第 3 级  无头加载打印成功标记 → 进程能起来并输出明确 ready 标记
第 4 级  产物数值指标        → 渲染帧 ROI 标准差、聚类差异、像素统计
第 5 级  全闭环端到端指标    → 成功率、reward 曲线、帧数对账
```

**关键补充：必须校验产物真实落地。** `genie_sim_v3 · L7`/`Q26` 出现过 **G1–G4 全 PASS 而贴图目录实际为空**（产物留在中转目录没 copy 出来）。
**动作**：**从产物文件出发解析相对路径，确认被引用文件真实存在且体积合理**——不要只查"引用写没写"。

### 5.2 成功判定只能信环境返回的信号

`lw_benchhub · L05`（**本次复现最危险的坑**）：

> 管线在"技能都跑完了"时也返回 `success=True`，**8 个 episode 全是失败轨迹却全部标为成功**。不报错、不崩溃、安静地污染数据集。

**两条配套规则**：
1. 成功判定取自**环境返回的信号**，不取自管线自报的 `success`。
2. **`terminated` 必须在 `step` 返回的瞬间捕获**——向量环境包装器会自动 reset，事后查询读到的是**下一个 episode 的初始状态**（`lw_benchhub · P35②`）。

### 5.3 无法直接观察结果时，把主观判断转成机器可判定的断言

`genesis_world · L03`：执行方没有读图能力，"机器人学会走路了吗"本来无法回答。拆成三层：

```
MP4 结构合法（ffprobe）
  + Train/mean_reward 末值 > 首值（tensorboard）
  + checkpoint 可加载且 iter 正确
  → 三层全 PASS 才算数
```

最终得到 reward **−0.179 → +13.24**、episode_length **19 → 997** 这样无可辩驳的证据。

**做法**：① 优先用**已有的数值日志**（tensorboard、JSON 指标）；② 视觉结论用**像素统计**替代（蓝色掩码占比、帧差、红色像素占比 36.6 % → 14.8 %）；③ 把整套检查封装成 **exit-0 脚本**；④ **明确写出该协议不能证明什么**。

### 5.4 假阴性同样要防：0 分不等于模型不行

**这是 `ge_sim_v2` 最贵的一次错判**（`L01`）：同一个"0 分"可以是两种完全不同的东西——

- Stage 3 的 0 % —— **假阴性**，判分文本错位造成（`P35`）。
- Stage 5 的 0 分 —— **真实测量**，跨任务域 + 跨机型迁移的诚实结果（`P40`）。

区分它们靠的不是直觉，是 §3.4 的**审计四件套**。**先证明管道是通的，再讨论模型行不行。**

### 5.5 口径纪律：降低目标之前必须先证明不可达

本知识库里有一对**形式相似、性质相反**的决策，值得当判据用（`genesis_world · L04`·`§3.1`）：

| | 做法 | 结果 |
|---|---|---|
| ❌ `genesis_world · D08` | **先改口径、后解释**——"抬起做不到，那就算触碰 <3.5 cm"，此时并无证据表明抬起不可达 | **掩盖了失败**，制造出假阳性 `P09`。根因分析自己指出：六次尝试的通过率提升**完全来自口径变更，而非能力提升** |
| ✅ `genesis_world · D18` | **先证明不可达、再经用户批准改目标**——13 次探针 + 明确的夹爪运动学机制解释 | **正确止损** |

> **判据：降低目标之前，必须先把"当前目标不可达"证明到机制层面，并且这个降级要显式征得决策者同意。**

**同源纪律**：
- **诚实测量优先于好看分数**（`ge_sim_v2 · L08`/`D17`）：明知矫正量纲能把分数抬上去，仍选择记录不矫正并写明定位。后续对照实验**回过头证明了这个判断是对的**——正因为没做手脚，那个 0 分才可以被当成可信基线去解释。
- **主动降低结论强度**（`genesis_world · D20`）：不说"数学零穿透"，只说"所有帧实测最小间距 ≥ −thickness，**未检测到穿透事件**"，因为采样分辨率不足以支撑更强宣称。
- **声明失败的成本远低于让假结果流入交付**（`lw_benchhub · D15`）：明确标记 **BLOCKED** 而非绕过。

### 5.6 把教训固化成测试，而不是固化成文档

`ge_sim_v2 · L03`：同一个坑在该项目至少**换皮复发三次**。

> **文档拦不住复发，因为下次踩的时候没人在读文档。**
> 有效的固化方式按可靠性排序：
> **单测断言 > 启动脚本里的固定动作 > 代码注释 > 文档**

证据：进了 mock 断言的两条协议陷阱 → 线上 8994 帧零协议错误；只写进文档的那条 → 复发。

### 5.7 编写测试用例的通用原则（汇总）

```
□ 每个断言都有可判定的数值阈值，不用「看起来对」
□ 断言产物真实落地（解析相对路径 → 文件存在 + 体积合理）
□ 断言输出随输入变化（同一检查喂两组不同输入，结果必须不同）
□ 成功取自环境信号，不取自管线自报
□ 关键版本 / 配置生效性回读断言（numpy 版本、__file__、total_spheres > 0）
□ 协议类做 round-trip 断言，别只做单向序列化
□ 明确写出「本测试不能证明什么」
□ 长跑前先跑 1/100 规模的全阶段 smoke test
```

## 6. 文档与记录

### 6.1 复现过程中应当维护的记录

按"后续复用价值"排序：

| 记录 | 为什么值得 | 实例 |
|---|---|---|
| **问题台账**（现象 / 根因 / 解决 / **无效尝试**） | "无效尝试"列省下的时间最多——它直接阻止后人重走死路 | 四个项目的 `troubleshooting.md` 均含 ❌ 无效尝试栏 |
| **决策表**（决策 / 原因 / 依据 / **代价与遗留** / 事后评价） | **"代价 / 遗留"列比"决策"列更值得读**——它记录的是这个选择买单的地方 | `ge_sim_v2 · §3` 明确这样设计 |
| **计划变更点表**（变更 / 触发原因 / **类型**） | 变更"类型"（外部不可控 / 文档与代码脱节 / 主动简化 / 自我纠正）能揭示系统性风险 | `genie_sim_v3 · §2.3` 的七个变更点 |
| **版本落差声明** | 原理层与实践层往往不是同一版本，命令不可跨版本套用 | `genesis_world`：原理层是 v1.3.3，其余四层实测 v1.2.2 |
| **只读资产清单** | 防止后续阶段覆盖已完成阶段的产出 | `lw_benchhub · D18`：**失败轨迹原样保留不覆盖，并加显式警告 README**，避免后人误把失败数据当示教数据 |
| **全量原始观测落盘** | 事后想查的东西，事中没记就没了 | `ge_sim_v2 · L07`：8994 帧 + 元数据**同时支撑了 0 分审计与跨机型量纲测量**，这是当时没预料到的回报 |
| **阻塞期的交接文档** | 卡住时不硬耗，转而产出可交接的东西 | `genie_sim_v3`：一次 1 h 43 min 阻塞期间产出 **8 份交接文档**（含完整性校验脚本） |

### 6.2 编号纪律

本知识库的约定，建议任何复现项目沿用：

```
P（问题） D（决策） L（教训） Q（FAQ） E（事件）
→ 只追加、不重排、不复用
```

外部交叉引用依赖此约定。四个项目的 `Qxx` ↔ `Pxx` 一一对应（排障层是经验层同一批事实的另一个视图）。

### 6.3 未解决的东西要显式留档

**不要把未收口的记录写成结论。** `ge_sim_v2 · Q41`/`P41` 明确标注"未解决"（源料内部记录自相矛盾且未收口），并要求"引用前先读该条原文，不要当成已验证结论"。同理 `genie_sim_v3 · 第九章` 专列"未解决 / 仅部分解决的问题"。

**还有一类值得留档：计划完成但从未执行的部分。** `genesis_world` 的 Patch 01/02 只有计划、没有任何执行记录，其中的 API 写法**未经验证**——文档里必须写清这一点，否则后人会把它当成已验证方案照抄。

### 6.4 推荐的文档分层（本知识库的五层结构）

```
quickstart.md            速查层  ⭐ 动手前先读：最短路径 + 常见问题 + 自检清单（派生层，不含新事实）
background_knowledge.md  原理层  是什么、怎么设计、API 与限制（固定 9 章）
ai_knowledge.md          经验层  实战踩坑、决策复盘、可复用教训（固定 8 章，全篇 [实践] 级）
troubleshooting.md       排障层  按报错现象查的 Q&A（由经验层 §4 派生，顶部必须有症状索引表）
code_knowledge.md        代码层  代码在哪、怎么启动、改哪个文件（固定 8 章，描述复现仓库而非上游）
```

**分层的关键价值不是分类，而是明确"冲突时以哪层为准"**：

- 原理层的修复建议若被实践推翻 → **以经验层的事后结论为准**，并在原理层就地标注冲突。
- 代码层指出某坑已被上游修掉 → 若在新版本上部署，**以代码层的上游对比结论为准**。
- 速查层与其余各层冲突 → **以被引用的那一层为准**（速查层只是入口）。

## 7. 一页速查：新工具链复现的动作序列

```
【准备】
  1. clone 上游源码到本地，给每条资料标证据等级          → §1.1
  2. nvidia-smi 查 compute_cap / RT cores / 显存 / 磁盘   → §1.2
  3. 找出硬绑版本的包，写成锁定清单                       → §1.3
  4. 判断是否需要多环境隔离（依赖正面互斥就隔离）          → §1.4
  5. ⭐ 逐条把计划里的技术假设 grep 到源码（尤其否定式断言）→ §1.5 / T1

【安装】
  6. 按 pip / 源码 / Docker / conda-CUDA 的准则选安装方式  → §2.1
  7. 边界画在目录上：跨容器操作要么全内、要么全外          → §2.2
  8. 配置一律「加法而非改法」（patch / staging / vendoring）→ §2.3
  9. 下载完整性可断言（查 206、校验哈希）                  → §2.4
 10. 装完就断言装上了（__file__、版本回读、判定是哪一份）   → §2.5

【运行】
 11. ⭐ 先跑 1/100 规模的全阶段 smoke test                → §3.1
 12. 铺可观测性：python3 -u / 真实 pid / 全量落盘          → §3.3
 13. 给长任务设独立于日志的存活判据 + 硬超时               → §3.2
 14. 排障过三道闸门：现象真的存在？修复真的生效？管道通了？ → §3.4
 15. 静默失效清单逐条加断言                                → §3.5

【调优】
 16. 先分类：是慢，还是根本没在工作（架构不匹配/缺硬件/跑CPU）→ §4.1
 17. 先降数据量，再优化实现；量化每次取舍                  → §4.2 / §4.3

【验收】
 18. 分级门禁 + 数值阈值 + 产物真实落地                    → §5.1
 19. 成功只信环境信号；0 分先跑审计四件套排假阴性           → §5.2 / §5.4
 20. 要降目标先证明不可达并征得同意                        → §5.5
 21. 把教训写成单测，而不是写成文档                        → §5.6

【记录】
 22. 问题台账（含无效尝试）/ 决策表（含代价）/ 计划变更点   → §6.1
 23. 编号只追加不复用；未解决与未执行的显式留档            → §6.2 / §6.3
```
