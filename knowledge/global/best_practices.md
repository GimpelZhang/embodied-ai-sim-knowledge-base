## 1. 计划与假设核验（写码之前）

### 1.1 🔁🔁🔁🔁 任何写进代码或配置的名字，落笔前 grep 到它的定义处或读取处

- **理由**：这是四个项目**唯一一条全部独立总结出来**的教训，也是复发频率最高的一条。失败形态是**静默无效**（配置照收、日志照打、行为不变），不是报错，所以不 grep 就永远发现不了。
- **要 grep 到什么**：配置键 → **读取它的代码**（不然它就是一行无效注释）；字段/API 名 → 它真的存在；注册 ID → `register(...)` 调用处（不然运行期才 `NameNotFound`）；关节/链接名 → URDF 或 USD 里真有（注意 **USD prim 路径 ≠ URDF 链接名**）。
- **示例**：`lw_benchhub · L02` 复发 ≥5 次（`P25`/`P26`/`P33`/`D17` + 一个不存在的机器人 ID）；`genesis_world · L05` 形态多样（`gs.morphs.Franka` 类不存在、`"hand"` 链接名不存在、`set_ipc_link_filter` 源码零命中、`head_link2` 其实是 USD prim 路径）；`ge_sim_v2 · L02` Stage 4 前置核验 2 小时拦下 9 处，执行期 **0 error**。
- **推论**：**文档、模型卡片、计划书都不是契约，源码才是。** 且诊断输出不得来自硬编码字符串 —— 那会让无效配置看起来在正常工作。

### 1.2 尤其要核验「否定式断言」

- **实践**：计划里凡出现「不需要 X」「不消费 Y」「可以传 `None`」这类否定式假设，必须单独核验。
- **理由**：**肯定式断言错了会立刻报错；否定式断言错了往往运行到一半才缺东西**，此时前面的时间已经花掉。
- **示例**：`ge_sim_v2 · L02`（`P21` 死在这上面）。

### 1.3 开工第一步是读源码核对计划，而不是执行计划

- **实践**：把「计划假设 vs 实际代码」的差异整理成一张表放在文档最前面，并明确写「不要再去找计划里的那些脚本」。
- **理由**：**快速迭代的开源仿真项目里，文档滞后于代码是常态而非例外。**
- **示例**：`genie_sim_v3 · L3` —— 七个计划变更点中**三个**源于「计划里的东西在 release 中不存在」（脚本、目录、WebUI、向量检索组件、专用入口）。
- **附带陷阱**：**上游脚本常假设有人坐在终端前**（交互式 `read`），非交互环境会直接挂死。

### 1.4 🔁🔁 参考实现先过小规模 smoke test，再投入长时运行

- **实践**：把正式参数按 1/100 缩小（iterations、envs、steps），**完整跑通全部阶段**（尤其是产物交接处），再放大。
- **理由**：**规模越大、单次运行越贵，smoke test 的杠杆越高**；而 API 缺陷几乎总是在产物交接处才暴露。
- **示例**：`genesis_world · L01` —— Stage 3 的五处真实 API 缺陷全部由 smoke test 在正式训练前捕获；其中 rsl-rl 的 **0-based checkpoint 编号**（`learn(50)` 只产出 `model_49.pt`）若未提前发现，会等到第 3 阶段才 `FileNotFoundError`，**前面数小时训练全部作废**。

### 1.5 第三方文档管协议，实测管 API

- **实践**：**先读文档拿协议，再用两条只读命令实测校准 API，之后才写代码。**
- **理由**：协议层（数据 schema、序列化变体、关节布局、生命周期）文档通常准确；而 API 层（登录方法、地址、SDK 是否存在、配额、id 形态、状态机）经常与线上不符。
- **示例**：`ge_sim_v2 · L04` —— wire 层协议**照写一次通过**，但 **HTTP API 层有 6 处与线上不符**。
- **配套分诊启发式**：**4xx 是语义拒绝 → 改请求而不是重试；5xx 先怀疑自己再怀疑平台。**

### 1.6 仿真器的真实能力边界要读源码确认，不能读计划书或宣传材料

- **实践**：验证「某功能是否真的生效」时，直接找到它的**执行路径**（哪个分支、什么条件才走到），而不是看它的**配置项是否存在**。
- **理由**：**配置项存在但空转的假开关很常见。**
- **示例**：`genesis_world · L08` —— 读 `fem_solver.py` 才确认**只有耦合器是 `IPCCoupler` 时 FEM 才做刚-柔接触，否则它只积分内部力**；不读源码会一直以为是参数没调对。同族的 `get_contacts()` 属 rigid-rigid 管线、PBD 粒子根本不参与。跨项目同类：`lw_benchhub` 的 `enable_corruption=True` 是空转假开关（**没有任何 `ObsTerm` 传 `noise=`**）。

## 2. 环境与依赖管理

### 2.1 🔁🔁 依赖需求正面互斥时，直接隔离环境，不要尝试调和

- **实践**：**一个工具一个 env，用文件在磁盘上交接，而不是在同一进程里交接。**
- **理由**：试图合并只会陷入版本连锁 —— 报错会一路变形（`UnicodeDecodeError` → 类不存在 → `OverflowError`），每一步都像新问题。
- **示例**：`genie_sim_v3 · L5` —— 两个重建工具对同一库版本需求互斥并连带牵动 numpy 主版本，隔离成两个 env 是**唯一可行解**；`ge_sim_v2` 复现用了**三个 conda 环境**，靠 `conda run` + 显式拼 `PYTHONPATH` 跨环境调用。
- **两个高频细节**：① **PEP 517 构建隔离会看不到已装的 torch** ⇒ torch 依赖型扩展一律加 `--no-build-isolation`；② `conda activate` 不把 env 的 bin 传给子进程 PATH，torch 的 `shutil.which` 检查会**误报缺少构建工具**。

### 2.2 安装新依赖前，先评估它的传递依赖会不会摧毁主环境

- **实践**：① 先 `pip install --dry-run` 或 `pip download` 看解析结果；② 高风险依赖装进**独立环境**验证；③ 主环境装任何东西前，先确认哪些包有**硬版本绑定**。
- **理由**：**一个可选特性的安装，可以让整个项目归零。**
- **示例**：`genesis_world · L06` —— `pip install pyuipc` 拉入 numpy 2.5.1 → `Numba needs NumPy 2.4 or less` → `import genesis` 失败 → **Stage 1/2/3 的成果全部不可运行**。
- **⚠️ 反直觉点**：`pip --target` 隔离**不够** —— 运行时 numpy 仍会冲突。
- **同族实例**：`lw_benchhub` 的 `numpy==1.26.0` **必须最后装，且每次 pip 操作后重新锁回**（Isaac Sim 的 C 扩展硬绑该版本）；`ge_sim_v2` 的 conda 装 CUDA 12.1 被解析成 13.x。

### 2.3 先查硬件能力，再装任何需要现场编译的 CUDA 扩展

- **实践**：把 `nvidia-smi --query-gpu=name,compute_cap` 当作**第 0 步**，并把值显式写进 `TORCH_CUDA_ARCH_LIST`；换 GPU 后**必须重编译所有扩展**。
- **理由**：CUDA 架构不匹配的报错**几乎从不指向真因** —— 驱动返回 `cudaErrorNoBinaryForGpu` 后上层框架回落 CPU dispatcher 并错算内存需求，于是**伪装成显存问题**。
- **判据（很好用）**：**显存请求数字荒谬（远超物理显存、或极小张量报 OOM）= 架构问题，不是容量问题。**
- **示例**：`genie_sim_v3 · L1` —— 同一根因以**三种面貌**出现（运行时 kernel crash、100 元素张量报 OOM、请求 56.60 GiB），共浪费数小时，**修复只需重编译 5 分钟**。

### 2.4 跨容器边界的文件操作，要么全程在容器内做，要么全程在宿主机做

- **实践**：开工第一步就把共享目录整体 `chown` 到容器 UID；**软链接必须在容器内用容器内路径创建**。
- **理由**：容器 UID 与宿主用户 UID 不同，两侧交替写同一批文件会反复 `PermissionError`，且逐个 `chmod` **治不了新生成的文件**。
- **示例**：`genie_sim_v3 · L4` —— 同一根因踩了 3 次。
- **两个附带陷阱**：宿主机创建的软链接存的是**宿主机绝对路径，容器内解析不到**；放在 tmpfs 下手工补齐的文件**重启即丢，且重填后还须重建容器**（旧容器挂的是空目录快照）。

## 3. 调试纪律

### 3.1 🔁🔁🔁 先量化「X 是否真的发生」，再写修复代码

- **实践**：写任何修复代码之前，先跑一次**未打补丁的 baseline**，用最便宜的手段（一次埋点、一行 grep）确认目标现象确实存在。
- **理由**：这是本知识库里代价最大的两个教训之一。不做这一步，你会为一个**根本不存在的现象**反复打补丁，而每一轮都"合理"。
- **示例**：`lw_benchhub · L01` —— `P30` 里一次接触力埋点（约 **3 分钟**）本可以省掉三轮碰撞修复 + 九次 descend 调试；`genesis_world · L02` —— Stage 1 前三次尝试都在调控制器参数，而 OpenVLA 的输出**与目标位置无关**，控制器再准也没用。
- **附加条款**：**跨运行的观察必须绑定 seed 与场景。** `lw_benchhub` 的一次反转就是把 A 场景观察到的位移当成 B 场景的 bug 去修 —— 记忆和文档里记的现象，可能来自另一次运行。

### 3.2 🔁🔁 「输出是否随输入变化」是一个独立的健全性检查

- **实践**：把"改变输入 / 改变变量，输出有没有变"当作一个**先于检查输出值本身**的独立检查项。
- **理由**：**如果一次修改改变了变量，而结果分毫不变，说明这个变量没起作用，或者你要修的问题不存在。** 这个信号比任何输出值都更早暴露问题。
- **示例**：`lw_benchhub · L03` —— 三次不同的碰撞修复得到**完全相同**的位移值；可达性门 v2 对三个不同场景算出**完全相同**的通过率（它压根没读场景）。`genesis_world · L02` —— 改 `pos_scale`、改 PD 增益，末端**依然收敛到同一点**，这个信号出现三次才被正确解读。
- **动作**：每轮修复前先写下"如果这个假设成立，我应该观察到什么数值变化"；若修复后该数值纹丝不动，**下一步不是提第 N+1 个假设，而是质疑问题的定义**。

### 3.3 🔁🔁🔁 给每个长任务预设「独立于日志的存活判据」

- **实践**：不要用"日志还在刷"判断任务活着。预设一组**外部可观测**的存活判据 + 一个硬性超时上限。
- **理由**：**日志有输出 ≠ 任务在推进。** 主线程刷屏而 worker 已死是仿真类长任务的典型形态。
- **可用判据（直接抄）**：
  ```
  ① GPU 利用率仅 1–2% 且显存占用为 0   → 渲染或初始化已失败
  ② 端口只有 LISTEN 没有 ESTABLISHED   → 客户端从未真正连上
  ③ 服务就绪只认日志里的明确标记        → 不认 docker ps 的 Up 状态
  ④ 预设「某标记超过 N 分钟未出现就 kill」的硬上限
  ⑤ 某步耗时超过预期 2 倍即视为异常
  ```
- **示例**：`genie_sim_v3 · L2` —— 至少三次遇到"进程 99% CPU、日志持续刷屏、实则已死"，最贵一次 **1h43min**；`lw_benchhub · L07` —— 一次 **58 分钟**挂起。

### 3.4 🔁🔁🔁 长跑调试的四条硬规则

- **实践**：
  1. **一次只改一个变量** —— 否则结果有歧义。
  2. **异常处理必须打完整 traceback**，不能只存 `repr(e)`。
  3. **必须设外部 wall-clock 超时并预留强杀手段**。
  4. **`python3 -u`** —— 否则后台日志可能是空的。
- **理由**：Isaac Sim 类仿真每次启动**约 3 分钟起**，调试成本高到不允许含糊的实验。
- **示例**：`lw_benchhub · L07` —— `P31` 的 9 次实验之所以有效，就是靠**严格单变量**；`ge_sim_v2 · L07` —— 不加 `-u` 时后台日志为空（`P30`）。
- **两个操作细节**：`pkill -f` 要用**方括号技巧**避免自杀；`os._exit()` 前要**显式 flush**。

### 3.5 「换个更好的组件」往往只是换了根因的名字

- **实践**：换组件前问一句 —— **"如果换了之后还不行，下一个解释会是什么？"** 如果能立刻说出下一个借口，说明当前根因没有定到底。
- **理由**：根因有层级。换组件只消除了当前那一层的名字，下一层会立刻顶上来。
- **示例**：`genesis_world · L07` —— 换用宣称"无 Embodiment Mismatch"的微调模型，末端仍在 18–36 cm 处不收敛，根因只是从 embodiment mismatch 变成了 **sim-to-sim gap**（训练/推理两侧物理引擎、渲染器、相机模型全不同）。真正奏效的是**换问题**，而不是换组件。

### 3.6 环境变量关不掉代码里写死的函数调用

- **实践**：环境变量不起作用时，去找**驱动那个行为的配置文件或代码行**，别加第二个环境变量。
- **理由**：`TORCH_COMPILE_DISABLE=1` 这类开关**关不掉源码里显式的 `torch.compile()` 调用**。
- **示例**：`lw_benchhub · L04`（`P19`）—— 对 HF 模型而言，源头通常是缓存里的 `config.json`（改 blob，记得备份）。
- **同族**：`ge_sim_v2` 的 `XLA_PYTHON_CLIENT_PREALLOCATE=false` 必须在 `import` **之前**生效；`genesis_world` 复现仓库把 `HF_HOME` 用 `os.environ[...] = ...` **硬写死在 `import torch` 之前**，在 shell 里 export 无效。

### 3.7 依赖某个 `reset()` / 复用某个有状态实例之前，先确认它到底重置了什么

- **实践**：依赖某个 reset API 前先 `inspect.getsource()` 看实现；复用有状态实例时**宁可显式 reset 或干脆重建**。
- **理由**：**隐式状态耦合从代码表面看不出来。**
- **示例**：`lw_benchhub · L08` —— `plan()` **不重置**技能实例的内部步计数器 ⇒ 复用实例导致**轨迹从未执行**；规划器的 `reset()` 只清图规划缓冲与随机种子，**不清 per-batch 结果累积器**。

## 4. 静默失效：本领域的头号敌人

> 这一节是四个项目**共同的最贵教训**（🔁🔁🔁🔁 4/4）。核心命题：**最贵的失败是不报错的失败。**

### 4.1 不要以「没报错」为成功，要为「成功」设一个可断言的判据

- **实践**：给每一个"它成功了吗"的问题配一条**可机器断言的判据**，而不是靠缺少异常来推断。
- **理由**：四个项目里代价最高的问题**全部不报错**。它们不崩溃、不刷红字，安静地污染下游。
- **对照表（`ge_sim_v2 · L05`，可直接抄作检查清单）**：

  | 现象 | 看起来 | 实际 | 该设的判据 |
  |---|---|---|---|
  | 下载"成功" | 文件下完了 | 截断损坏 | 查 HTTP 206 / 校验和 / 体积 |
  | 进程消失 | 日志干净 | 被内核 SIGKILL | 查 `dmesg` |
  | 数据布局排错 | 不报错 | **行为错** | round-trip 断言 |
  | numpy 进 msgpack | 本地测试正常 | 对端解析崩 | 协议 round-trip |
  | `import` 成功 | 没报错 | 导入的是**空壳命名空间包** | 查 `__file__` |
  | 跑完出分 | 流程正常 | **结论是错的** | 帧数对账 + 管道审计 |

- **同族清单（`lw_benchhub · L06`）**：碰撞球定义被忽略而 `total_spheres=0` 不报错 / IK 被降级为 stub / 配置里的自定义键无人解析 / **键名不匹配只打 warning，权重静默随机初始化** / LLM 静默降级但 HTTP 仍 200 / 重试计数器被重置导致上限永不触发 / **评测进程报错后仍 exit 0**。
- **通用对策**：给每个"配置生效了吗"的问题写一个**最小验证脚本**（断言 `total_spheres > 0`、回读响应体的 `model` 字段、`assert numpy.__version__ == ...`）。**"配置解析通过 ≠ 配置生效"。**

### 4.2 成功判定只能信环境返回的信号，不能信管线自报的 `success`

- **实践**：成功与否只取环境/仿真器返回的终止信号，**不取上层管线自己算的布尔值**；且 `terminated` 必须**在 `step()` 返回的瞬间捕获**。
- **理由**：管线往往把"技能都跑完了"当成功。反向也成立：向量环境包装器会**自动 reset**，事后查询读到的是**下一 episode 的初始状态**。
- **示例**：`lw_benchhub · L05` —— 管线在"技能都跑完了"时返回 `success=True`，**8 个 episode 全是失败轨迹却全部标为成功**，本次复现最危险的坑。

### 4.3 一个常量被两个以上的读取方消费时，必须单点定义

- **实践**：**判据很简单 —— 如果一个值有两个以上的读取方，它就必须有且只有一个定义处。**
- **理由**：否则它迟早会在其中一处过期，**而且不会报错**。
- **示例**：`ge_sim_v2 · L06` —— `SOURCE_TASK_TEXT` 同时喂给策略 prompt、世界模型 `set_task`、判分器标准，其中一份留着上一阶段的过期文本，导致判分器看着不存在的物体打分；修好三处后**成功率 0 % → 6.5 %**。另一例 `final_<tag>.json` 在两个脚本里各硬编码一遍。
- **同族**：`genesis_world` 复现仓库的 Stage 4 判定阈值在 demo 顶部常量与 `verify_stage4.py` 的 `DEMOS` 字典里**各写一遍**，只改一边会出现"demo 自认为通过、verify 判 FAIL"。
- ⚠️ **本库有一处罕见的负面样例**：这条教训**在产出它的同一个仓库里被违反了至少四次**（`ge_sim_v2/code_knowledge.md` §8.2）—— 说明"知道"和"做到"之间还差一个机制，见 §8.1。

### 4.4 同一个坑会换皮复发；写进单测比写进文档可靠

- **实践**：固化方式按可靠性排序 ——
  ```
  单测断言  >  启动脚本里的固定动作  >  代码注释  >  文档
  ```
- **理由**：**文档拦不住复发，因为下次踩的时候没人在读文档。**
- **示例**：`ge_sim_v2 · L03` —— 至少复发三次；进了 mock 断言的两条（`P36`/`P37`）线上 **8994 帧零协议错误**，只写进文档的 `P28` **复发了**。

## 5. 验证与成功判定

### 5.1 🔁🔁🔁 把主观判断转化为可机器判定的数值断言

- **实践**：① 优先用**已有的数值日志**（tensorboard、JSON 指标）；② 视觉结论用**像素统计**替代；③ 把整套检查封装成 exit-0 脚本；④ **明确写出该协议不能证明什么**。
- **理由**：肉眼判断"看起来对了"在视觉类任务里极不可靠；而在无头/远程/自动化环境里根本没有肉眼。
- **示例**：`genesis_world · L03` —— "机器人学会走路了吗"被拆成三层可判定断言（MP4 结构合法 + `Train/mean_reward` 末值 > 首值 + checkpoint 可加载且 `iter` 正确），最终得到 reward **−0.179 → +13.24**、episode_length **19 → 997** 这样无可辩驳的证据；`genie_sim_v3 · L7` —— 分级门禁，每级带可判定数值（静态校验 → prim/材质计数 → 无头加载打印成功标记 → 渲染帧 ROI 标准差 → 全闭环像素指标）。

### 5.2 验证必须校验产物**真实落地**，不只校验引用写没写

- **实践**：**从产物文件出发解析相对路径，确认被引用文件真实存在且体积合理。**
- **理由**：只检查结构的验证门会放过假绿灯。
- **示例**：`genie_sim_v3 · L7` —— 出现过 **G1–G4 全 PASS 而贴图目录实际为空**（产物留在中转目录没 copy 出去）。

### 5.3 下结论前先审计管道 —— 「审计四件套」

- **实践**：任何"模型不行 / 泛化失败 / 分数不合理"的结论之前，先跑这四项：
  ```
  ① 回退计数    —— 兜底 / except / default 分支触发了几次？（要求 0，且触发必被记录）
  ② 动作非退化  —— 动作 std、关节位移、夹爪开合，是不是在输出常数？（恒定 = 模型没在输出）
  ③ 帧数对账    —— 落盘帧数 = 元数据行数 = 各日志帧计数之和？
  ④ 输入侧量纲  —— 观测的量纲、分位、静息位形，是否落在训练分布内？
  ```
- **理由**：**同一个"0 分"可以是两种完全不同的东西** —— 假阴性（管道故障）或真实测量。区分它们靠的不是直觉。**先证明管道是通的，再讨论模型行不行。**
- **示例**：`ge_sim_v2 · L01`（本项目最贵的一条）—— Stage 3 首轮的 0 % 是**假阴性**（判分文本错位），Stage 5 的 0 分才是**真实测量**；反过来做，就会为一个不存在的"泛化失败"找三轮解释。

## 6. 目标管理与诚实交付

> 这一节讨论的都是**时间紧张时最容易发生**的事。四个项目里，形式最相似、性质最相反的一对决策就在这里。

### 6.1 🔁 正确的加速是「先降数据量，再优化实现」

- **实践**：某条路径太慢时，**先把输入规模降两个量级看还慢不慢**，再考虑换实现、换库、换算法。
- **理由**：数据量是最便宜的旋钮，且常常"几乎免费"。
- **示例**：`genie_sim_v3 · L8` —— 卡在纯 Python 光栅化时**试了五种加速库全失败**，正解是**先激进抽面把面数降两个量级**，之后连纯 numpy 向量化都只需 **5–20 秒**（原为 3 小时）。同族：该项目 3DGS 点云 **600K → 100K** 换来约 **16×** 吞吐，而平均像素差仅 **1.13**。

### 6.2 🔁🔁🔁 降低目标之前，必须先把「原目标不可达」证明到机制层面，并显式征得决策者同意

- **实践**：写下"我为什么认为原目标不可达"的**机制性解释**（不是"试了很多次不行"），提交给决策者，**再**改目标。
- **理由**：本知识库里有一对**形式相似、性质相反**的先例，值得反复对照：

  | | 做法 | 结果 |
  |---|---|---|
  | ❌ 反面 | `genesis_world · D08` —— **先放宽判定口径**，而当时并无证据表明目标不可达 | 掩盖了失败，制造出**假阳性** `P09` |
  | ✅ 正面 | `genesis_world · D18` —— **13 次探针 + 夹爪运动学机制解释 + 用户批准**，然后止损 | 本库最值得模仿的一次止损 |

- **同族反面**：`genie_sim_v3 · L8` 记录了两次质量事故都源于"我有更聪明的方法" —— 用顶点色顶替 UV 贴图流程（该项目自评"最大耻辱"）、绕过规范流程改用替代算法（**同时掩盖了真正的 CUDA 根因**）。
- **纪律**：如果确实要偏离计划，必须**显式记录偏离项与代价**，**不能在交付时把替代方案描述成已完成原目标**。自设的合格线未达到时，要么返工，要么写明为何接受 —— **静默放过会在后续阶段以数倍成本回来**。

### 6.3 诚实测量优先于好看分数

- **实践**：**口径一旦为了好看而动，后面所有基于它的结论都不可信。** 宁可记录难看的原始数字，并在报告里写清它的适用范围。
- **理由**：干净的测量在事后会以你没预料到的方式派上用场。
- **示例**：`ge_sim_v2 · L08` —— `D17` 明知矫正量纲能把分数抬上去，仍选择不矫正、在报告里写明"跨任务域 + 跨机型"的定位；后来的对照实验（同一链路换官方权重得 0.745 / 0.604）**回过头证明了这个判断是对的** —— 正因为没做手脚，那个 0 分才可以被当成可信基线去解释。
- **配套**：分数不可外推时要**显式声明**。`ge_sim_v2` 的 RWR 实验把成功率从 30 % 拉到 80 %，但判分器是自补的替身而非官方 World Judge ⇒ 该分数**只能内部对比、不可外推**，文档里就这么写。

### 6.4 明确写出「本次验证不能证明什么」

- **实践**：每套验证协议都附一段"不在考核范围内"的说明。
- **理由**：避免用不可控项否定可控成果，也避免读者把结论用超范围。
- **示例**：`genie_sim_v3 · L7` —— 明确"策略得分属模型能力，与资产升级无关"，因此不用它否定资产升级的成果；`genesis_world · L03` —— 验证协议末尾明写它不能证明什么。

## 7. AI 辅助执行（Agent 驱动复现）的用法

> 这四次复现均由 AI Agent 执行，以下是**关于怎么用 Agent** 的教训，与前面"怎么做工程"的教训是两回事。

### 7.1 让模型产出结构化代码 / DSL 时，示例的价值远高于描述；且防御必须冗余

- **实践**：① 贴**完整可运行的 EXEMPLAR** 让模型模仿，而非让它凭记忆写；② 合法资产 / 枚举值要 `ls` 出**真实白名单**注入 prompt，并在每条 spec 里**显式钉死 id**（防幻觉）；③ 输出清洗**双保险** —— prompt 声明禁用 markdown 围栏 **且** 代码侧正则强 strip；④ 失败时把上一次的报错**反馈回去**重试。
- **理由**：仅用自然语言描述 API 约束时，模型对**函数签名**的"记忆"会失准（参数顺序调换、多传关键字参数）。
- **示例**：`genie_sim_v3 · L6` —— Round 2 **3 个场景全部因此失败**；补上"合法签名逐条清单 + 一份已成功运行的完整示例"后**一次通过**。

### 7.2 Agent 执行时，把「计划文档」当唯一真值源，但把「源码」当唯一契约

- **实践**：计划文档决定**做什么**（偏离必须显式记录），源码决定**能怎么做**（§1.1 的 grep 纪律）。两者不可互换。
- **理由**：Agent 在时间压力下有两种典型偏移 —— 一是自作主张换方法（`genie_sim_v3 · L8` 称计划的"宪法地位"），二是照文档/记忆写出不存在的 API（§1.1 的 4/4 收敛教训）。这两条纪律各治一种。

### 7.3 Agent 没有的能力，要在协议层补上

- **实践**：凡 Agent 无法直接感知的结论（看图、听声、主观质量），**必须先转成它能读的数值**，见 §5.1。
- **理由**：`genesis_world · L03` 的原话是"执行方没有读图能力，'机器人学会走路了吗'本来无法回答"。这不是模型缺陷，是**协议设计问题** —— 补上像素统计与指标日志后就可回答，而且证据比肉眼更硬。

### 7.4 文档不是给 Agent 的固化机制

- **实践**：要让某条纪律真的生效，把它写进**单测 / 启动脚本的固定动作**，不要只写进文档（详见 §4.4）。
- **理由**：**下次踩坑的时候没人在读文档** —— 对 Agent 尤其如此，它每次都是新的上下文。
- **⚠️ 本库的实证**：`ge_sim_v2` 的"常量单点定义"教训（§4.3）**在产出它的同一个仓库里被违反了至少四次**。这是"写进文档 ≠ 会被遵守"的最直接证据。

## 8. 知识固化与可观测性

### 8.1 固化机制按可靠性选，不要默认选文档

```
单测断言  >  启动脚本里的固定动作  >  代码注释  >  文档
```

- **示例**：`ge_sim_v2 · L03` —— 进了 mock 断言的两条线上 **8994 帧零协议错误**；只写进文档的那条**复发了**。

### 8.2 长流程的可观测性要在**开跑前**铺好

- **实践**：开跑前的固定动作清单（直接抄）：
  ```
  □ python3 -u                        否则后台日志可能是空的
  □ pid 文件记「真实」子进程            不是包装进程；.pid 可能根本不可用于清理
  □ 显存用 nvidia-smi 对账              不看日志自报
  □ 进程猝死查 dmesg                   traceback 不会有
  □ 观测 / 中间结果全量落盘             事后想查的东西，事中没记就没了
  ```
- **理由**：**事后想查的东西，事中没记就没了。** 而全量落盘的回报常常超出预期。
- **示例**：`ge_sim_v2 · L07` —— Stage 5 的 **8994 帧 JPEG + 元数据**，事后**同时**支撑了 0 分审计和跨机型测量，"这是当时没预料到的回报"。

### 8.3 把「计划假设 vs 实际代码」的差异表放在文档最前面

- **实践**：复现文档开头就写一张差异表，并明确告诉后来者"**不要再去找计划里的那些脚本**"。
- **理由**：这是后来者最容易重复浪费时间的地方。
- **示例**：`genie_sim_v3 · L3` 的"N 个关键差异速读"。本知识库把这个模式制度化成了每个项目的 `00-index.md` **`未提及` 清单**与 `quickstart.md`。

### 8.4 版本落差必须显式标注，且要说明「哪一层的结论可以跨版本用」

- **实践**：文档里凡有版本落差，写清 **API 写法不可跨版本套用；能力边界类结论可以**。
- **理由**：这是本知识库内部最大的引用陷阱。
- **示例**：`genesis_world` 原理层核对 **1.3.3**、其余四层实测 **1.2.2**；`genie_sim_v3` 原理层是 v3.2.0 的 `geniesim` CLI、经验层与代码层是 3.0 时期的 `app/app.py`。两者都在文档头显式声明了落差。
