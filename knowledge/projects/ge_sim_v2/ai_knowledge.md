## 1. 复现目标与背景

### 1.1 想验证什么

复现的目标不是"把仓库跑起来"，而是回答一个更具体的问题：**能不能用一个神经视频世界模型替代物理仿真器，构成一条可用的 VLA 策略评测闭环？** 围绕这个问题，复现被切成五个递进的阶段：

| 阶段 | 要回答的问题 | 结论 |
|---|---|---|
| Stage 1 | 单条闭环能不能跑通？速度如何？ | 能跑通；**wallclock 0.88 帧/s，约 18× 慢于实时** |
| Stage 2 | 能不能低成本造出成规模的泛化场景？ | 能；用 R2E2R 从 1 条真实 demo 生成 **46 个** |
| Stage 3 | 批量评测下策略的泛化表现如何？ | **OSR 6.5 %**（且是跨任务，不是同任务空间泛化） |
| Stage 4 | 能不能**在世界模型里**做策略自进化？ | 能；留出集 **30 % → 80 %** |
| Stage 5 / 5b | 这套策略拿到第三方线上评测上是什么水平？ | 自训权重零样本 **0 / 0.0725**；官方 baseline **0.745 / 0.604** |

### 1.2 起点上的三条硬约束

这三条贯穿全程，很多决策只有放在它们下面才讲得通：

1. **网络在国内**。pip 官方源、pytorch.org、HuggingFace 的 xet 后端全部阻断或极慢，几乎每个阶段都要先解决"东西下得下来吗"（见 `P01`–`P05`）。
2. **`/` 盘极紧、`/mnt` 后期也满到 98 %**。用户反复强调"所有安装下载都放 `/mnt`"，到 Stage 3 起又不得不全部改道家目录。磁盘直接催生了 `D07`（符号链接影子树）这类看起来很怪的设计。
3. **单卡 A800-SXM4-40 GB，宿主内存 47 GB，驱动与系统 CUDA 冻结不可动**。40 GB（**不是计划里假设的 80 GB**）限定了 Stage 4 的微调规模，47 GB 宿主内存则在 Stage 5b 直接导致了一次静默 OOM（`P32`）。

另有一条工作方式上的约束：**执行 Agent 没有读图能力**，用户每个阶段都明确"不要试图查看图像，用别的方式 debug"。这意味着所有视觉结果的判定都必须转成可量化的通道——要么走 MiMo 判分，要么走数值统计（动作 std、关节位移、帧数对账）。`L01` 的"审计四件套"本质上就是这条约束逼出来的方法论。

### 1.3 被测对象与判分方
- **世界模型**：GE-Sim 2.0 社区蒸馏权重（G01 + OmniPicker 本体）。
- **被测策略**：π0.5（openpi），Stage 1 训练产出的检查点，训练任务是**水壶 / 洗面奶 / 毛巾**三项。
- **判分方**：Stage 1–4 用**小米 MiMo `mimo-v2.5`** 充当 World Judge（官方 World Judge 未开源，见 `D01`）；Stage 5/5b 的判分完全在 RoboColiseum 平台侧（Isaac Sim 自动判分），我们既不参与也无法干预。

> ⚠️ **一个贯穿全文的重要前提**：被测策略训练于水壶/洗面奶/毛巾，而 Stage 2 之后的评测任务是 `lift_box`（搬箱子）。因此 Stage 3 的 6.5 % 与 Stage 5 的 0 分**都是跨任务域的迁移测量**，不是同任务下的失败。这个前提被误读过一次，代价是整整一轮全量重跑（`P35`）。

## 2. 计划与执行流程

### 2.1 实际时间线

| 时间 | 阶段 | 产出 |
|---|---|---|
| ~07-30 | Stage 1 计划 | 原计划 + 两个 Patch（澄清 World Judge 概念、接入 MiMo）合成本地可执行计划 |
| 07-30 ~ 07-31 | Stage 1 执行 | 环境 ~1.5 h + 权重下载 ~2 h + 闭环 rollout 739 s；3 个 demo 出分 |
| 07-31 | Stage 1 追加 | 帧率取证专项（本项目最硬的一组性能数） |
| 08-01 ~ 08-04 | Stage 2 | R2E2R 场景生成，46/50 episodes |
| 08-05 ~ 08-08 | Stage 3 | 批量闭环评测，OSR 6.5 % |
| 08-07 | 专题 | VLA ↔ 世界模型交互接口的代码级剖析 |
| 08-09 ~ | Stage 4 | RWR 在世界模型内自进化，30 % → 80 % |
| Stage 4 后 | 回溯复查 | 用户提出 Stage 1 三 demo 动作雷同的质疑（**无执行记录**，见 `P41`） |
| 08-22 ~ | Stage 5 | RoboColiseum 线上评测，自训权重零样本 |
| Stage 5 后 | Stage 5b | 换官方 baseline 权重同平台重跑，做对照 |

### 2.2 每个阶段共同的执行套路

五个阶段用的是同一套流程，且这套流程本身就是复现能推进下去的原因之一：

```
① 读原始计划 → 由 planner 产出「适合本地执行的详细计划」
② （Stage 4 起新增）逐条源码核验计划   ← D10，本项目最高价值的一步
③ 新建 feature-stageN 分支，不影响既有阶段的功能
④ 执行，边跑边记坑
⑤ 产出「完整执行纪要」文档，重点写调试过程与坑
⑥ 更新项目 CLAUDE.md，合入 main
```

用户在每个阶段的指令里都固定强调四件事：**在新分支下开发**、**不打折扣执行哪怕等待时间长**、**不要泄密**、**不能影响此前阶段的功能**。第四条尤其重要——它把"改上游代码"变成了高成本操作，于是催生了 `D05`（幂等 patch 文件）、`D09`（合成 staging 文件而非改上游）这类"加法而非改法"的设计。

### 2.3 流程上的一次关键进化

Stage 1–3 是"边写边撞"，Stage 4 换成了"**先核验再写**"：在动手写任何代码前，花约 2 小时把计划里每一条技术假设拿到源码里逐条对照，**一次性抓出 9 条致命错误**（见 `D10`、`P24`–`P26`）。

对照效果很直白：

| | Stage 1 | Stage 4 |
|---|---|---|
| 计划与源码不符 | 10 处，**在执行中逐个撞出来** | 9 处，**在执行前一次性拦下** |
| 执行期报错 | 大量，跨 8 个坑 | **0 error / 0 abort** |

Stage 5 把这条经验又推进一层：不仅核验源码，还**在上线前用 6 项 mock 断言把协议陷阱钉死**（`D20`），结果是**线上评测本体一次报错都没有**。

## 3. 关键决策与原因

`D01`–`D20`，按发生顺序。**"代价 / 遗留"一列比"决策"一列更值得读**——它记录的是这个选择买单的地方。

| # | 决策 | 原因 | 代价 / 遗留 |
|---|---|---|---|
| **D01** | 用小米 **MiMo `mimo-v2.5`** 充当 World Judge | 论文主打"自带可验证奖励"，但 **World Judge 奖励模型未开源**，开箱即用时 `reward`/`progress` 恒为 `None`（原理层 §6.6） | 判分依赖外部 API：网络、配额、以及 `P18` 那种"HTTP 200 但没内容"的隐蔽失败都成了闭环的一部分 |
| **D02** | 关闭 `sparge_attention` 等加速内核，回落 SDPA | `spas_sage_attn` **根本不在 PyPI 上**，须源码编译；上游也明说没有它照样能跑 | 推理更慢。**但这条应当成为所有新部署的默认动作**——配置文件默认把四个内核开关全开是个陷阱（原理层 §5.4） |
| **D03** | 自研分块下载器，弃用 `curl -C -` | 镜像会 302 跳转，CDN 间歇返回 200 而非 206，`curl` 的续传语义在这种情况下**静默截断**（`P02`） | 多写一个脚本；但换来的是"下载完整性可断言"，是整个 Stage 1 里回报最高的一次重写 |
| **D04** | Stage 2 的源任务从 `mug_to_basket` 改为 `lift_box` | 前者缺 `preprocess_seededit` 提示词，直接 `NotImplementedError`（`P19`） | **这是全项目影响最深远的一次改动**：它让评测任务与策略训练任务分了家，直接埋下 `P35` 的假阴性，也决定了 Stage 3/5 的分数必须按"跨任务迁移"解读 |
| **D05** | inpaint 改走 `b64_json` 内联，并固化为**幂等 patch 文件** | 上游模型已下架，且默认的 `url` 返回走 CDN 国内不可达（`P20`）；用户要求"不能影响既有阶段功能" | patch 需随上游演进维护；但比直接改上游代码可回滚、可审查 |
| **D06** | 放弃手写的 5×10 批采样器，改用 R2E2R 原生 `n_gen_per_source` + `mode: full_random` | 自己写之前没读全上游能力，写完才发现是重复造轮子 | 一次架构返工。教训归入 `L02` |
| **D07** | 用**逐文件符号链接**搭影子目录树 | 视频输出路径硬编码在上游、而该盘只剩 6.6 G（`P33`） | 每 episode 12 个链接，脆；**注意是文件级软链，目录级软链在这里不管用**——上游会往目录里写新文件 |
| **D08** | 渲染改为**每 clip 一个独立子进程** | RSS 跨 clip 单调增长，~6 个 clip 后必被 OOM-kill（`P31`） | 进程启停开销。**进程内 `gc` 试过，只能解跨条目累积，解不了条目内峰值**——这是被验证过的无效方案 |
| **D09** | 用 `build_bundle(staging_dir=…)` 现场合成 4 个 `.npy`，而不是改上游 | 闭环路径仍会从磁盘读这 4 个小文件（`P21`），但改上游违反"不影响既有阶段"约束 | 每 episode 多 ~1 KB 临时文件；换来上游零改动 |
| **D10** | **Stage 4 起：写码前先逐条源码核验计划** | Stage 1 在执行中撞出 10 处计划-源码不符，成本极高 | 前置约 2 h。**回报是 9 条致命错误在写码前被拦下、执行期 0 error**——本项目最值得复制的一条流程决策 |
| **D11** | 放弃 REINFORCE，改用 **RWR（奖励加权回归）** | π0.5 的 `forward()` 是流匹配速度 MSE，采样是 `@torch.no_grad` 的 10 步 Euler，**没有闭式概率密度**，策略梯度无从算起（`P25`） | RWR 不是严格的策略梯度；但它能直接复用模型原生的可微损失，是此处唯一能落地的路线 |
| **D12** | 策略改为**进程内加载**，不走 WebSocket 服务 | `Policy.infer()` 末尾是 `np.asarray(...)`，一道**硬 numpy 屏障**，梯度过不去（`P26`） | 训练进程与推理服务不再共用一套启动路径，多维护一个入口 |
| **D13** | 只解冻 4 个真实 Linear（**2,165,792** 参数），冻结主干 | peft/LoRA 路线不成立（`P24`）；且 40 GB 显存放不下全量微调 | 表达能力受限；但 60 iteration 就拿到 +50 pp，说明在这个任务上够用 |
| **D14** | Stage 5：**agent 零 GPU，策略集中**——4 个 agent 进程共享一个策略服务器 | 单卡要同时喂满两个 job 的并行度 | agent 与策略间多一跳本地 WS，~350 ms/推理。**Stage 5b 用官方 in-process agent 只要 ~85–100 ms，这一跳的代价被量化了** |
| **D15** | **fail-safe 但绝不静默**：handler 异常回 no-op 包络，同时在状态 JSON 里记 `policy-error-fallback` | 平台侧规定成功响应里出现顶层 `error` 会被判 fatal；但静默兜底会制造假数据 | 无。**这条设计是后来 `L01` 审计能成立的前提**——"回退计数为 0"之所以是有力证据，正因为回退一旦发生必被记录。本次 0 次触发 |
| **D16** | 线上评测的烧配额步骤藏在环境变量开关之后，默认只跑离线部分 | 防误触 | 无。多一个显式开关而已 |
| **D17** | 跨机型量纲/分位差异**记录但不矫正** | 静默矫正会让分数好看，但测的就不再是零样本迁移能力了 | 分数难看（instruction 0 分）。**但换来结论可信**，且在 Stage 5b 的对照中被证明是对的判断 |
| **D18** | Stage 5b **直接用官方 agent，不重写适配层** | 官方 agent 内建了我们 Stage 5 手写的全部陷阱处理（`.tolist()`、warmup 空帧、相机改名、状态拼接、waist 维度） | 无。**结论是反过来的**：Stage 5 自己重写适配层属于负优化，只有"官方 SDK 未发布"能为它辩护 |
| **D19** | agent **错峰 120 s 启动** | 4 个 jax 进程并发 restore，峰值 ~11–12 GB RSS × 4 > 47 GB 宿主内存，必被 OOM killer 静默杀（`P32`） | 冷启动总时长变长；无其它代价 |
| **D20** | 上线前用 **6 项 mock 断言**把协议陷阱钉死（plain-msgpack round-trip、`wm[j]=j` 重排、空帧、包络形状、horizon 截断、no-op 兜底） | 线上每次试错都烧配额且慢 | 前置写测试的时间。**回报是线上 8994 帧零协议错误** |

### 3.1 两条被证伪的思路（值得单独记住）

- **"闭环路径不消费任何录制轨迹字段，全部可以传 `None`"**——计划里的断言，**部分为假**。即使用 `conditioning="action"`，渲染器初始化仍会从磁盘读 4 个 `.npy`。教训是：*"不消费某数据"这类否定式断言，必须在源码里验证到读取处，不能靠接口语义推断*（`P21`、`L02`）。
- **"用进程内 `gc` 解决渲染内存增长"**——试过，无效。它只能压住跨条目的累积，压不住单条目内的峰值。唯一可靠解是进程隔离（`D08`）。

## 4. 遇到的问题与解决方案（核心章）

### 4.6 F 类 · 平台契约与判分口径（`P42`–`P45`）

|---|---|---|---|---|
| **P42** | 平台返回的 board 总分**与文档描述的算法不符**：manip 只有一个任务拿到 0.725、其余 9 个为 0，总分却是 **0.0725** | 平台 skill 文档明写 `task total = 各 episode 之和`、`job total = 各 task total 之和`，但实测**总分是各任务分数的算术平均**：Stage 5b 的 manip 十任务和 6.04 → 报 **0.604**、instruction 和 7.46 → 报 **0.745**，**除以 10 后与平台报数吻合到 ≤0.001** | 按**均值**理解总分；跨 board 不可比，同 board 内才有意义。报告里所有分数标注来源快照 | 按文档的"求和"口径解读 —— 会把 0.0725 误读成"接近满分的十分之一"之类的错误结论 |
| **P43** | 计划里"平台调度 **78 个**标准化任务"、"四榜各 20/20/20/18"，报告模板甚至预填了"综合平均成功率 62.5%"与行业 baseline 百分比 | 计划作者未访问平台，凭推测写数字并写进了**报告模板** —— 比写进正文更危险，因为模板会被当成待填的既定事实 | 勘误表直接判"**78 是未经验证数字**"，任务数改为从 `/result` 的 `tasks` keys 实测（实测 instruction / manip **各 10 个**）；并立规矩"**报告中不存在任何无法溯源到 `results/` 快照的数字**" | 保留占位数字待后续核对 —— 占位数字一旦进模板就会被沿用 |
| **P44** | `GET /api/challenge/job/<uuid>/result` 返回 **500 `invalid job_id`** | 该接口只接受**数字 job id**（如 1140 / 1141），不接受 uuid；而 uuid 才是拨隧道用的标识 | 先 `GET /api/challenge/jobs`（响应键是 **`items`**，不是 `jobs`），建立 `items[].job_uuid → items[].id` 映射并落盘，轮询与报告全用数字 id | 把 500 当平台故障干等 —— **5xx 先怀疑自己**（`L04`） |
| **P45** | 计划中的"**桌高 / Z 轴泛化衰减曲线**"分析做不出来 | 生成配置 `trans_range.generate.object` 把 **Z 分量钉死为 0**，46 条 episode 的 `dz` 实测**全为 0.000** —— 数据里根本没有高度变化。另：`obj_trans_vec[0]`（dx）**恒为负**，`obj_rot_angle` 原始值**未解卷绕**（需 `mod 2π`） | **删除该分析维度**，并在报告里加一条显式的"Z 轴声明"说明无数据支撑（`L09`） | 硬做曲线 —— 自变量方差为 0 时，任何"衰减曲线"都是噪声 |

> **`P42` 引用纪律**：这是**实测与文档冲突**，不是文档笔误——两处都留档，但**引用总分语义时以实测的均值为准**（原理层 §9.3.4 已就地标注）。它同时解释了为什么 Stage 5 的 instruction 榜是干净的 **0**：10 个任务全 0，均值自然是 0。

### 4.7 全章速查：最容易重复踩的六个

如果只记六条：

1. **`P35`** 一个常量被多方消费 → 假阴性。落笔任何共享常量前，grep 出它的**全部**消费者。
2. **`P02`** 断点续传遇 200 而非 206 → 静默截断。下载完整性必须可断言。
3. **`P32`** OOM-kill 无日志无 Traceback → 只有 `dmesg` 知道。
4. **`P28`** `conda run` 包装 pid ≠ 真实子进程 → 显存不还（**复发过一次**）。
5. **`P36`** 多套关节布局并存 → 错了不报错，只是行为错。用单测钉死。
6. **`P43`** 计划里的数字（任务数、拆分、乃至报告模板里的"成功率"）**没有一个可以凭想象填** → 任何进入报告的数字必须能溯源到 `results/` 快照。

### 5.1 做得好的

| 表现 | 证据 |
|---|---|
| **流程会自我进化** | Stage 1 边写边撞（10 处计划-源码不符），Stage 4 改为先核验后写码（9 条致命错误前置拦下，执行期 0 error），Stage 5 再加一层上线前 mock 断言（线上 0 报错）。**同一个团队在三个阶段里把方法论迭代了两轮** |

| 问题 | 证据 | 应当怎么做 |
|---|---|---|
| **计划阶段大量假设未经核实** | Stage 1 计划 10 处与源码不符；Stage 2 计划**外部资源假设 6 处全错**（仓库 404、模型选错、数据集形态错、**连显卡显存是 40 GB 还是 80 GB 都写错了**） | 计划里每一条外部事实（仓库存不存在、接口签名、硬件规格）落笔前必须验证。`D10` 就是对这条的补救 |

### 5.3 用户介入的价值（三次关键拦截）

值得单列，因为这三次都不是 Agent 自己发现的：

1. **Stage 3 判分标准错位**（`P35`）——用户主动指出"Stage 2 泛化的是搬箱子任务，不能再用 Stage 1 的评价标准判分"。**这一句拦下了一个即将成型的错误结论。**

## 6. 可复用的经验教训

`L01`–`L09`。按**通用价值**排序，第一条是本项目最贵的一条。

### `L01` · 下结论前先审计管道，别急着解释结果

同一个"0 分"，可以是两种完全不同的东西：
- Stage 3 首轮的 0 % —— **假阴性**，判分文本错位造成（`P35`）。
- Stage 5 的 0 分 —— **真实测量**，跨任务域 + 跨机型迁移的诚实结果（`P40`）。

区分它们靠的不是直觉，是**审计四件套**：

```
① 回退计数    —— 兜底路径触发了几次？（要求：0，且触发必被记录，见 D15）
② 动作非退化  —— 动作 std、关节位移、夹爪开合，是不是在输出常数？
③ 帧数对账    —— 落盘帧数 = 元数据行数 = 各日志帧计数之和？
④ 输入侧测量  —— 观测的量纲、分位、静息位形，是否落在训练分布内？
```

**先证明管道是通的，再讨论模型行不行。** 反过来做，就会像 Stage 3 那样为一个不存在的"泛化失败"找三轮解释。

### `L02` · 写码前，把计划里每条技术假设核验到源码

Stage 1 撞了 10 处，Stage 4 前置 2 小时拦下 9 处、执行期 0 error。两个数摆在一起，这条不需要再论证。

**尤其要核验否定式断言**（"不需要 X"、"不消费 Y"、"可以传 `None`"）——`P21` 就死在这上面。肯定式断言错了会立刻报错，否定式断言错了往往表现为运行到一半才缺东西。

### `L03` · 同一个坑会换皮复发；写进单测比写进文档可靠

本项目至少复发三次：`P28`（Stage 3 → Stage 5）、`P07`（自写代码 → 官方代码）、`P30`（Stage 3 → Stage 5）。

**文档拦不住复发，因为下次踩的时候没人在读文档。** 有效的固化方式按可靠性排序：

```
单测断言  >  启动脚本里的固定动作  >  代码注释  >  文档
```

`P36`/`P37` 进了 mock 断言，线上 8994 帧零协议错误；`P28` 只写进了文档，于是复发。

### `L04` · 第三方文档管协议，实测管 API

Stage 5 的核心方法论：官方 SKILL 描述的 **wire 层协议**（观测/动作 schema、msgpack 变体、关节布局、隧道生命周期）**照写一次通过**；但 **HTTP API 层有 6 处与线上不符**（登录方法、地址、SDK 是否存在、配额数字、id 形态、状态机）。

**正确姿势**：先读文档拿协议，再用两条只读命令实测校准 API，之后才写代码。配套的分诊启发式很好用——**4xx 是语义拒绝，改请求而不是重试；5xx 先怀疑自己再怀疑平台**。

### `L05` · 最贵的失败是不报错的失败

本项目的静默失败清单：

| 现象 | 看起来 | 实际 |
|---|---|---|
| `P02` 下载"成功" | 文件下完了 | 截断损坏 |
| `P32` 进程消失 | 日志干净 | 被内核 SIGKILL，证据只在 `dmesg` |
| `P36` 布局排错 | 不报错 | 行为错 |
| `P37` numpy 进 msgpack | 本地测试正常 | 对端解析崩 |
| `P23` import 成功 | 没报错 | 导入的是空壳命名空间包 |
| `P35` 跑完出分 | 流程正常 | 结论是错的 |

**共同对策：为"成功"设一个可断言的判据，而不是以"没报错"为成功。** 下载查 HTTP 206、import 查 `__file__`、协议做 round-trip、结果做帧数对账。

### `L06` · 一个常量被多方消费时，必须单点定义

`P35` 的 `SOURCE_TASK_TEXT` 同时喂给策略 prompt、世界模型 `set_task`、判分器标准；`P39` 的 `final_<tag>.json` 在两个脚本里各硬编码一遍。

**判据很简单：如果一个值有两个以上的读取方，它就必须有且只有一个定义处。** 否则它迟早会在其中一处过期，而且**不会报错**。

### `L07` · 长流程的可观测性要在开跑前铺好

事后想查的东西，事中没记就没了。开跑前的固定动作：

- `python3 -u`（否则后台日志是空的，`P30`）
- pid 文件记**真实**子进程，不是包装进程（`P28`）
- 显存用 `nvidia-smi` 对账，不看日志（`P28`）
- 进程猝死查 `dmesg`（`P32`）
- 观测/中间结果全量落盘 —— Stage 5 的 8994 帧 JPEG + 元数据，**事后同时支撑了 0 分审计和跨机型测量**，这是当时没预料到的回报

### `L08` · 诚实测量优先于好看分数

`D17` 明知矫正量纲能把分数抬上去，仍选择记录不矫正、在报告里写明"跨任务域 + 跨机型"的定位。Stage 5b 的对照实验（同一条链路换官方权重得 0.745 / 0.604）**回过头来证明了这个判断是对的**——正因为没有做手脚，那个 0 分才可以被当成可信的基线去解释。

> 反面参照：本知识库另一个项目里有过"放宽判定口径掩盖失败"的先例，制造了一个假阳性结论。**口径一旦为了好看而动，后面所有基于它的结论都不可信。**

### `L09` · 派生分析的可行性受生成配置约束 —— 先验证数据分布，再承诺分析维度

计划里写好的"桌高 / Z 轴泛化衰减曲线"在 Stage 2 数据落盘后被证明**根本画不出来**：`trans_range.generate.object` 把 Z 分量钉死为 `0.0`，46 个 episode 的 `dz` 实测**全部为 0.000**，自变量方差为零（`P45`）。同类问题还有两个：`dx` 恒为负（平移只朝一个方向采样），`obj_rot_angle` 未做 `mod 2π` 归约（分布展开到约 ±1000°，直接画直方图会得到无意义的长尾）。

**规则**：任何"随 X 变化的曲线 / 分组对比"类分析，在写进计划**之前**要先回答两个问题——① 生成配置里 X 是否真的被采样（grep 到 `*_range` 的定义处）；② 落盘数据里 X 的实测方差是否非零（统计 `meta_info.json` 而不是相信配置）。答不出就别写进计划，更别写进报告模板（`P43`）。

**做不到时的正确姿势不是硬凑，而是显式声明**：Stage 2 最终删掉该分析维度，并在报告里补一条"Z 轴声明"，说明这批数据是**平面内平移 + 绕 Z 旋转**的分布，Z 向泛化能力**未被本批数据覆盖**。这样下游引用者不会误以为"测过且通过"。

> 与 `L06`（常量单点定义）同源的一点：配置项的**真实取值**必须从配置文件读，不能从计划文档或记忆里抄——本项目已因此栽过多次（`P43`、`P45`）。
